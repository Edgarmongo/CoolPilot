## 一、执行原则

1. **先审计，再修改。** 先确认现有实现和调用关系，不重复造轮子。
2. **先修数据流，再扩展业务。** 优先解决 Asset 身份、引用和保存一致性。
3. **不随意改数据库。** 优先复用现有表、字段、模块；新增表或迁移必须先说明必要性并获得确认。
4. **每个子阶段独立冻结。** 验收通过后记录 Commit、测试结果、修改文件、未解决事项和冻结边界。

## 十一、子阶段执行协议
把下面这份协议作为每次开发任务的固定前置要求。

### 1. 单一范围
本次只执行指定子阶段。不得顺带执行下一阶段，不得扩展为相关模块重构。

### 2. 修改前
- 检查 Git 工作区，保护用户已有修改。
- 阅读相关实现、测试和冻结文档（**先读 §二 已冻结面，确认不会重写**）。
- 列出计划修改文件、调用链、预期行为变化。
- 如发现需要修改数据库结构、冻结契约或其他阶段模块，先停止并说明原因，等待批准。

### 3. 实现约束
- 优先复用现有模块和接口。
- 不重复实现已有能力。
- 不引入未经批准的新表、状态机、依赖或配置体系。
- 不修改与本阶段无关的文件。
- 不删除用户数据，不执行破坏性迁移。
- 不以放宽断言或删除测试来使测试通过。

### 4. 验收
- 为本阶段关键行为增加或更新测试。
- 运行与变更相关的测试。
- 在可行情况下运行类型检查、ESLint 和完整测试套件，命令见 §三。
- 如测试未运行、失败或环境受限，明确记录，**不得声称通过**。
- 检查最终 diff，确认没有范围外修改。

### 5. 完成报告
必须输出：
1. 子阶段 ID 和完成状态。
2. 修改文件及每项修改目的。
3. 实际执行的测试命令与结果。
4. Git Commit SHA；未提交则明确说明。
5. 数据库和配置是否变更。
6. 未解决问题与风险。
7. 本次冻结的行为边界。
8. 下一阶段的前置条件。

### 6. 停止规则
完成报告后立即停止，不自动开始下一阶段。
如果验收失败，先修复本阶段问题，不得转向新功能。

**不要把上面的全部内容交给编码工具。**

实际操作顺序是：

2. 检查 P0-01 报告，确认它没有修改任何文件。
