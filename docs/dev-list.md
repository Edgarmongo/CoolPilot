# CoolPilot 具体开发功能清单

这次把规划进一步落到可以直接拆分开发任务、逐项验收、完成后冻结的粒度。

我会以你现有的 CoolPilot 功能为基础，不重建已经完成的 AI Runtime、文章生成服务和辅助发布验证能力。下面每一项都包含：开发目标、具体功能、验收标准和实施顺序。

需要先明确：这是一份基于现有菜单盘点和此前审计结果整理的开发清单。尚未重新检查当前分支源码的项目，不会直接认定为已完成或存在缺陷；具体数据库字段也先不预设。

## 一、开发总览

P0 · 开发基线确认

锁定当前实现、未完成项和验收标准，不开发新业务功能。

规划与审计

P1 · Creator Workflow 1.0

Asset、草稿证据、创作保存、辅助发布与结果验证。

第一开发重点

P2 · Agent v0

任务、步骤、工具执行、审批、幂等、重试与恢复。

P3 · 人机协作与证据

任务可见、操作可控、执行可追踪、结果可审计。

P4 · 多平台适配

统一平台接入契约，同时保留各平台的独特行为。

P5 · 能力包与 Marketplace

Workflow、Agent、Template 的标准化、安装、升级和分发。

# 三、P1：Creator Workflow 1.0 具体开发清单

P1 是当前最值得集中开发的阶段。先把现有创作功能连接成一条可靠的工作流，再在这条工作流上建设 Agent。

## P1-01：统一 Asset 素材管理

目标： 图片、视频等文件有稳定的身份、来源、引用关系和生命周期。

| 编号 | 开发功能       | 具体要求                                         | 优先级 |
| ---- | -------------- | ------------------------------------------------ | ------ |
| A01  | Asset 身份规范 | 明确 Asset 的唯一标识、文件位置、类型与状态      | P0     |
| A02  | 统一素材解析   | 统一客户端和服务端对素材引用的解析方式           | P0     |
| A03  | 统一素材写入   | AI 生图、上传、远程导入、文章配图遵循统一规则    | P0     |
| A04  | 远程素材本地化 | 外部图片按既定安全策略导入本地工作区             | P0     |
| A05  | 内容关联素材   | 文章封面、正文图片等通过一致的引用规则关联 Asset | P0     |
| A06  | 产品素材关联   | 产品、品牌图片进入创作流程时保留来源与引用       | P1     |
| A07  | 素材引用查询   | 可以判断素材被哪些内容或任务使用                 | P1     |
| A08  | 素材删除保护   | 被引用素材不能被静默删除；删除行为必须明确       | P1     |
| A09  | 内部文件隔离   | 运行时截图、临时文件等不应混入用户素材库         | P1     |
| A10  | 文件可迁移性   | 为后续备份、导出和恢复保留稳定的文件关联         | P1     |

### A01–A05 的具体验收

- 图片上传后可以在内容编辑器中正确显示。

- AI 生成图片可以关联到指定内容。

- 从 URL 导入文章时，远程封面按规则本地化。

- 内容在编辑器、内容中心与发布流程中使用同一素材时，不会因路径格式差异而丢失。

- 图片引用顺序、封面选择和正文图片关系保持一致。

- 素材处理失败时能显示明确错误，不产生错误的成功状态。

- 现有四份重复的客户端图片解析逻辑被统一，服务端发布解析不再单独丢弃远程封面。

- 测试覆盖绝对路径、远程 URL、裸文件名及无效文件引用等现有输入形式。

### Asset 的实施边界

第一版不要求新增独立的 Asset 数据库表。如果现有数据库结构能够支持稳定身份与引用关系，优先复用；只有在现有结构无法表达必要关系时，才设计 schema 变更。

暂不包含：素材版本历史、智能去重、自动垃圾回收、完整视频编辑器。

## P1-02：完善内容草稿与保存

目标： 用户知道内容保存到了哪里、当前是什么状态、重新打开后能否继续编辑。

| 编号 | 开发功能         | 具体要求                                             |
| ---- | ---------------- | ---------------------------------------------------- |
| D01  | 草稿状态定义     | 明确 `draft`、`ready`、`posted` 等现有状态的业务含义 |
| D02  | 编辑保存反馈     | 清晰区分保存成功、保存失败和保存状态未知             |
| D03  | 重新打开草稿     | 重新进入内容后，恢复正文、标题、素材引用及必要配置   |
| D04  | 素材与草稿一致性 | 保存内容时，正文、封面与图片引用保持一致             |
| D05  | 草稿来源记录     | 明确内容来自手动创建、AI 生成、URL 导入或其他来源    |
| D06  | 草稿修改证据     | 最低限度记录必要的保存时间、来源和操作结果           |
| D07  | 保存失败恢复     | 失败后提供重试或恢复入口，避免用户误以为内容已保存   |

### 验收标准

- AI 生成的文章可以进入编辑器并保存。

- 手动创建、AI 生成和 URL 导入的内容遵循一致的保存规则。

- 重新打开后，标题、正文、封面和素材引用不丢失。

- 用户不会把“已填入编辑器”误认为“已保存到本地”。

- 保存失败时不应错误地将内容标记为已完成。

- 不要求在本阶段实现完整版本树、自动保存历史或多人协作。

## P1-03：补齐 Draft Evidence

Draft Evidence 记录的是一次平台草稿准备或交接的实际结果，不是用户本地保存的文章本身。

| 编号 | 开发功能       | 具体要求                               |
| ---- | -------------- | -------------------------------------- |
| DE01 | 草稿准备记录   | 标识对应内容、目标平台、帐号和准备操作 |
| DE02 | 字段级结果     | 记录标题、正文、图片等字段的准备结果   |
| DE03 | 失败字段说明   | 能定位哪些字段未成功处理               |
| DE04 | 交接结果       | 明确草稿是否已交给平台编辑器           |
| DE05 | 未知状态       | 页面中断或结果不明确时保留未知状态     |
| DE06 | 证据与内容关联 | 可以从内容找到相关草稿准备记录         |
| DE07 | 恢复入口       | 允许用户根据失败情况返回编辑或重新准备 |

### 验收标准

- 可以判断平台草稿是否真正准备完成。

- 可以识别具体失败的字段。

- 未知状态不被自动当成成功。

- 用户取消准备流程不会生成虚假的成功事实。

- 不破坏已冻结的 `DraftFieldOutcome`、`PublishDraftEvidence` 等现有契约。

- 是否持久化所有草稿尝试，需要按照既有 D2 设计边界决定，不默认改变已冻结的行为。

## P1-04：巩固 Publish Evidence

辅助发布成功验证已完成并冻结，因此本任务的重点不是重新实现，而是保护契约，并独立核实其他发布路径。

| 编号 | 开发功能         | 具体要求                                   |
| ---- | ---------------- | ------------------------------------------ |
| PE01 | 验证契约回归     | 保持现有辅助发布成功、失败、未知的判断规则 |
| PE02 | 发布事实一致性   | 核实发布记录与内容状态之间的更新关系       |
| PE03 | 防止重复发布     | 核实重复触发、重试和结果未知时的处理策略   |
| PE04 | 结果证据关联     | 发布记录可追溯到相应的验证结果             |
| PE05 | 自动发布路径审计 | 单独确认自动发布的状态更新和重复选择风险   |
| PE06 | 发布记录可查     | 用户能按内容、帐号、平台和结果查找发布记录 |

### 验收标准

- 仅凭 URL 变化不能将结果判定为成功。

- 发布结果未知时不会写入虚假的成功事实。

- 成功结果可以关联到有效证据。

- 自动发布路径不会因为内容状态未更新而无限重复选择同一内容。

- 已冻结的辅助发布测试继续通过。

- 对自动发布路径的修复单独立项，不混入冻结模块的无关重构。

## P1-05：打通端到端创作工作流

| 编号 | 开发功能       | 具体要求                                 |
| ---- | -------------- | ---------------------------------------- |
| WF01 | 创建创作任务   | 支持从现有创作入口发起内容生产           |
| WF02 | 生成与编辑交接 | 复用现有统一文章生成服务                 |
| WF03 | 保存内容草稿   | 通过现有内容管理能力保存结果             |
| WF04 | 关联素材       | 标题、正文、封面与图片素材保持一致       |
| WF05 | 选择发布目标   | 选择平台与帐号，并检查必要的输入条件     |
| WF06 | 准备平台草稿   | 调用现有辅助发布能力并保留草稿证据       |
| WF07 | 人工确认       | 发布前展示目标、内容和帐号，等待用户确认 |
| WF08 | 执行与验证     | 复用现有发布执行及结果验证机制           |
| WF09 | 展示最终结果   | 关联内容、发布记录和验证结果             |
| WF10 | 异常恢复       | 失败、未知、中断时保留可理解的状态       |

### P1 最终验收场景

- 正常生成、编辑、保存、关联素材、发布和验证。

- 保存草稿后关闭并重新打开应用。

- 远程封面导入、本地显示和发布。

- 素材缺失或上传失败。

- 草稿准备中途失败。

- 用户取消发布。

- 平台结果未知。

- 平台明确确认发布成功。

- 同一任务被重复触发。

- 应用重启后查看已有内容与发布记录。

P1 完成标准： 以上核心场景全部有明确的测试或验收结果。通过后冻结 Creator Workflow 1.0，再进入 Agent 开发。

# 四、P2：Agent v0 具体开发清单

P2 的目标是让 Agent 真正执行一条工作流，而不是只在聊天窗口里回答问题。

第一条 Agent 工作流建议直接复用 P1 已经验收的创作流程：生成文章 → 检查素材 → 等待用户确认 → 辅助发布 → 验证结果。

## P2-01：Agent 任务管理

| 编号 | 开发功能 | 具体要求                                             |
| ---- | -------- | ---------------------------------------------------- |
| AG01 | 创建任务 | 将用户的目标转化为持久化任务                         |
| AG02 | 任务身份 | 每个任务有稳定的唯一标识                             |
| AG03 | 任务状态 | 明确待执行、执行中、等待审批、失败、完成、取消等状态 |
| AG04 | 任务详情 | 保存目标、必要参数、当前步骤和最终结果               |
| AG05 | 任务列表 | 查看历史任务、当前任务和失败任务                     |
| AG06 | 任务关联 | 任务关联内容、Asset、帐号、工具调用及发布记录        |
| AG07 | 任务终态 | 明确完成、失败、取消及需要人工处理的情况             |

## P2-02：步骤与工具调用

| 编号 | 开发功能     | 具体要求                                           |
| ---- | ------------ | -------------------------------------------------- |
| AG08 | 步骤模型     | 将任务拆分成可追踪的执行步骤                       |
| AG09 | 工具注册     | 统一登记可供 Agent 使用的业务工具                  |
| AG10 | 工具参数校验 | 工具执行前验证输入参数                             |
| AG11 | 工具结果     | 统一表达成功、失败、未知和结构化输出               |
| AG12 | 执行事件     | 记录步骤开始、结束和错误                           |
| AG13 | 工具权限     | 根据操作风险与用户权限决定能否执行                 |
| AG14 | Runtime 复用 | 所有模型调用继续走现有 AI Runtime                  |
| AG15 | 业务能力复用 | 优先调用现有内容、Asset 和发布接口，不复制业务逻辑 |

## P2-03：审批、重试与恢复

| 编号 | 开发功能     | 具体要求                                           |
| ---- | ------------ | -------------------------------------------------- |
| AG16 | 人工审批节点 | 发布等关键操作前进入等待审批状态                   |
| AG17 | 审批结果     | 记录批准、拒绝或取消                               |
| AG18 | 重试策略     | 为每种工具明确是否可重试及重试条件                 |
| AG19 | 幂等保护     | 防止同一任务意外重复创建内容或重复发布             |
| AG20 | 结果未知处理 | 外部操作结果未知时，先查询或人工核实，不直接重做   |
| AG21 | 任务恢复     | 应用重启后可以恢复安全的未完成任务                 |
| AG22 | 任务取消     | 停止后续步骤，并明确已经发生的外部操作             |
| AG23 | 错误归类     | 区分模型调用失败、业务校验失败、平台失败和系统异常 |

## P2-04：Agent 执行界面

- 在任务列表中查看状态。

- 在任务详情中查看步骤进度。

- 查看工具调用及其结果。

- 查看等待审批的操作。

- 在允许的状态下重试或继续任务。

- 查看失败原因和恢复建议。

- 通过任务关联打开生成的内容与发布记录。

### P2 验收标准

1. Agent 能完成一条真实的创作工作流。

2. 每一步都有明确的执行状态。

3. 关键操作前必须经过人工确认。

4. 任务状态在应用重启后仍可恢复。

5. 重试不会无条件重复外部副作用。

6. 每项业务操作复用现有业务接口，模型调用复用 Runtime。

7. 至少完成一次正常流程、一次中途失败和一次结果未知场景的验收。

P2 暂不开发： 任意目标的通用规划引擎、多 Agent 协作、自主购买服务、无人监管的自动发布，以及完整的 Agent 市场。

# 五、P3：Human + Agent + Evidence 具体开发清单

P3 的重点是让用户可以检查、控制和解释 Agent 的行为。

## P3-01：任务执行透明度

- 展示任务目标、创建时间和当前状态。

- 展示每个步骤的执行状态与时间。

- 展示工具名称、输入摘要、输出摘要及错误。

- 展示生成内容、关联素材和发布结果。

- 区分模型解释、工具返回值和已验证的业务事实。

- 展示当前是否等待人工审批。

- 允许用户从业务对象跳转到相关任务记录。

## P3-02：人工控制中心

- 暂停支持暂停的任务。

- 审批待执行的操作。

- 拒绝不应执行的操作。

- 取消未完成任务。

- 从安全检查点继续执行。

- 对不可安全恢复的操作要求重新确认。

- 记录审批对象、审批结果及时间。

## P3-03：统一证据视图

- 查看任务执行事件。

- 查看内容草稿的保存信息。

- 查看平台草稿准备证据。

- 查看发布验证证据。

- 查看最终业务事实。

- 支持从发布记录回溯任务与内容。

- 对证据缺失或结果未知的情况进行明确提示。

## P3-04：权限与安全治理

- 为工具声明读取、写入、删除和外部发布等风险类型。

- 在工具执行边界执行权限检查。

- 确保模型不能绕过审批直接执行受控操作。

- 对敏感日志进行脱敏。

- 明确执行记录、证据和文件的保存与删除策略。

- 为高风险操作保留足够的审计信息。

### P3 验收标准

用户可以从任务详情中回答：

- Agent 做了什么？

- 为什么执行这一步？

- 实际返回了什么？

- 哪些操作经过人工批准？

- 发布成功的依据是什么？

- 如果失败，能否恢复？恢复会不会重复操作？

# 六、P4：多平台适配具体开发清单

P4 不应重新开发每个平台的整套业务，而是将平台差异放入适配层，让通用工作流可以复用。

## P4-01：平台能力定义

每个平台需要声明以下能力：

- 支持的内容类型：文章、图文、视频等。

- 支持的素材类型与约束。

- 标题、正文、话题和封面等字段要求。

- 是否支持平台草稿。

- 是否支持自动发布或只能辅助发布。

- 发布前是否需要特殊确认。

- 哪些信号可以证明发布成功。

- 哪些情况只能返回结果未知。

- 登录状态失效时如何处理。

- 上传失败或页面结构变化时如何处理。

## P4-02：统一适配接口

| 编号 | 开发功能 | 具体要求                                           |
| ---- | -------- | -------------------------------------------------- |
| MP01 | 平台注册 | 统一登记平台适配器                                 |
| MP02 | 能力声明 | 查询平台支持哪些内容与操作                         |
| MP03 | 内容映射 | 将通用内容映射为平台专属字段                       |
| MP04 | 素材映射 | 根据平台要求处理图片、视频和封面                   |
| MP05 | 草稿准备 | 使用统一输入输出契约执行平台草稿准备               |
| MP06 | 发布执行 | 区分自动发布、辅助发布和不支持的操作               |
| MP07 | 结果验证 | 返回成功、失败或未知，并提供对应证据               |
| MP08 | 错误映射 | 将平台错误映射为统一错误类别，同时保留原始诊断信息 |
| MP09 | 能力测试 | 每个平台独立维护能力与回归测试                     |
| MP10 | 平台配置 | 保存平台特定设置，避免污染通用内容模型             |

## P4-03：实施顺序

1. 选择一个现有平台作为标准适配器。

2. 将该平台的草稿、发布与验证流程接入统一契约。

3. 验证素材、失败、登录失效与未知结果场景。

4. 在不破坏现有工作流的前提下，接入第二个平台。

5. 根据真实差异完善适配器契约，而不是提前设计过度通用的接口。

6. 后续平台逐个接入并单独验收。

### P4 验收标准

- 新增平台时不需要复制核心 Agent、内容管理和证据系统。

- 每个平台的能力限制能够被明确表达。

- 平台特有字段不会丢失。

- 不支持的操作不会被伪装成支持。

- 发布成功判断仍然遵守统一证据规则。

- 已有平台的回归测试全部通过。

# 七、P5：Workflow、Agent、Template 与 Marketplace

P5 的前提是已有工作流与 Agent 能够稳定运行。只有可重复使用的能力，才值得产品化和分发。

## P5-01：标准能力包

- 定义能力包的唯一标识。

- 定义名称、描述、作者与适用场景。

- 定义版本号与兼容性。

- 定义输入参数与输出结构。

- 定义依赖的工具、模型能力和其他能力包。

- 定义权限要求与风险等级。

- 定义能力包的安装和卸载行为。

- 定义配置迁移规则。

- 定义能力包的来源和完整性验证。

## P5-02：本地能力管理

- 浏览已安装的 Workflow、Agent 和 Template。

- 安装本地能力包。

- 启用、停用和卸载能力包。

- 检查依赖是否满足。

- 检查能力包与当前 CoolPilot 版本是否兼容。

- 查看能力包声明的权限。

- 查看能力包的版本与更新记录。

- 更新失败后恢复至已知可用版本。

## P5-03：能力商店

- 浏览官方发布的能力包。

- 浏览用户发布的能力包。

- 按类别、关键词和兼容性筛选。

- 查看能力说明、版本、依赖与权限。

- 安装后验证能力是否可以正常运行。

- 对发布者、版本和来源进行必要的可信度校验。

- 提供能力包更新与回滚入口。

## P5-04：商业化验证

- 验证用户是否愿意复用其他人制作的能力。

- 验证创作者是否愿意分享或发布能力包。

- 验证哪些能力具有付费价值。

- 验证本地运行、BYOK 和用户数据所有权是否得到保持。

- 在真实需求明确后，再设计订阅、交易和收入分成。

### P5 验收标准

一个能力包可以被安装、检查依赖、按权限运行、升级和回滚。Marketplace 的交易功能只有在能力生态和真实需求得到验证后才启动。

# 八、建议直接采用的开发任务优先级

为了让清单能直接转成开发计划，建议把每项任务再分成三个等级。

- P0 优先级： 阻塞 Creator Workflow 1.0 的必要能力。

- P1 优先级： 完成核心工作流后必须具备的管理与治理能力。

- P2 优先级： 可以延后，不阻塞当前阶段验收的扩展能力。

| 开发顺序 | 任务编号     | 开发任务                     | 为什么先做                 |
| -------- | ------------ | ---------------------------- | -------------------------- |
| 1        | P0-01～P0-08 | 核实基线与缺口               | 避免重复建设和误判状态     |
| 2        | A01～A05     | Asset 身份、解析、写入和关联 | 内容、编辑器与发布共同依赖 |
| 3        | D01～D04     | 草稿状态与保存一致性         | 保证创作结果可靠保存       |
| 4        | DE01～DE07   | Draft Evidence               | 明确平台草稿准备与交接结果 |
| 5        | PE01～PE06   | 发布事实与验证契约           | 避免错误成功和重复发布     |
| 6        | WF01～WF10   | 端到端创作工作流             | 验收 Creator Workflow 1.0  |
| 7        | AG01～AG15   | Agent 任务与工具调用         | 在稳定业务能力上构建 Agent |
| 8        | AG16～AG23   | 审批、幂等、重试与恢复       | 让 Agent 安全执行真实任务  |
| 9        | P3-01～P3-04 | 人机协作与证据视图           | 提高可控性和可审计性       |
| 10       | MP01～MP10   | 多平台适配契约               | 降低后续平台扩展成本       |
| 11       | P5-01～P5-04 | 能力包与 Marketplace         | 在可复用能力成熟后商业化   |

## 当前最重要的三个开发交付物

1. Asset 统一管理： 文件身份、来源、引用关系和生命周期有明确规则。

2. Draft Evidence 与 Publish Evidence： 草稿准备和发布成功有不同的证据契约。

3. 端到端创作工作流： 从 AI 生成、编辑保存、素材关联到人工确认发布、结果验证完整贯通。

这三项完成并验收后，才开始建设完整的 Agent 任务执行能力。

执行原则：一次只推进一个可独立验收的子阶段，完成后记录提交、测试结果和冻结边界，再继续下一项。 不要把整份清单一次性交给编码工具执行，否则容易引入不必要的数据库重构、重复实现和范围扩张。
