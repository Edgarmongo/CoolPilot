# CoolPilot 开源项目能力提取与总体开发清单

> 目的：研究优秀开源项目，提取可复用的产品能力、架构设计和工程实践，逐步建设 CoolPilot AI 创作者生产平台。
>
> 核心原则：不简单复制代码、不盲目增加依赖、不偏离产品路线。每个阶段通过验收后，才能进入下一阶段。

---

## 一、CoolPilot 产品定位

CoolPilot 是一个 Local-first 的 AI 创作者生产平台。

核心目标是让用户在本地数据可控的环境中，利用 AI 完成内容创作、素材管理、媒体生产、多平台运营和自动化任务执行。

### 1.1 总体架构

```text
CoolPilot
│
├── AI Infrastructure
│   ├── Local-first
│   ├── BYOK
│   ├── Model Runtime
│   ├── Model Registry
│   ├── Credential Pool
│   └── Failover
│
├── Creator Workflow
│   ├── Content Generation
│   ├── Content Editor
│   ├── Asset Management
│   ├── Draft Evidence
│   ├── Assisted Publishing
│   └── Publish Evidence
│
├── Agent Execution
│   ├── Agent Loop
│   ├── Task Management
│   ├── Tool Registry
│   ├── Workflow Execution
│   ├── Human Approval
│   └── Failure Recovery
│
├── Human + Agent + Evidence
│   ├── Execution History
│   ├── Task State
│   ├── Business Facts
│   ├── Verification Evidence
│   └── Human Intervention
│
├── Multi-platform
│   ├── Platform Adapters
│   ├── Platform Capabilities
│   ├── Platform-specific Content
│   └── Publish Verification
│
└── Marketplace
    ├── Workflow
    ├── Agent
    ├── Template
    ├── Version Management
    ├── Installation
    └── Distribution and Commerce
```

### 1.2 产品原则

* [ ] Local-first：优先本地运行，用户掌握自己的数据。
* [ ] BYOK：允许用户使用自己的模型服务凭证。
* [ ] AI Runtime：所有 AI 调用统一经过现有 Runtime。
* [ ] Creator Workflow：先建立可靠的创作工作流。
* [ ] Agent：让 AI 执行真实任务，而不只是聊天。
* [ ] Evidence：区分执行过程、业务事实和验证证据。
* [ ] Human-in-the-loop：关键操作支持人工确认、暂停和接管。
* [ ] Multi-platform：抽象共性，但保留平台差异。
* [ ] Marketplace：先形成可复用能力，再建设能力市场。

## 二、开源项目研究清单

### 2.1 Remotion

仓库：https://github.com/remotion-dev/remotion

定位：基于 React 的程序化视频生成与渲染框架。

所属阶段：P1、P2、P5。

#### 值得研究的能力

* [ ] 使用代码定义视频场景。
* [ ] 参数化视频模板。
* [ ] 视频时间轴、动画和转场。
* [ ] 字幕、音频、图片与视频素材组合。
* [ ] 根据业务数据批量生成视频。
* [ ] 视频渲染任务管理。
* [ ] 渲染进度、错误和产物管理。
* [ ] 模板与业务数据分离。
* [ ] 通过代码和数据驱动视频内容。

#### CoolPilot 可提取的设计

* 视频模板与渲染引擎分离。
* 模板具有明确的输入参数。
* 输入素材使用统一 Asset 标识。
* 渲染任务拥有独立状态和执行记录。
* 渲染完成后，产物登记到 Asset 系统。
* 模板可以成为未来 Marketplace 的交付物。

#### 建议实施

P1：

* [ ] 明确视频文件属于 Asset 体系的哪一类。
* [ ] 明确视频任务产物如何登记。
* [ ] 不急于集成完整视频渲染引擎。

P2：

* [ ] 为 Agent 提供创建视频任务的工具。
* [ ] 支持提交、查询、取消和获取渲染结果。
* [ ] 为长时间渲染任务建立状态管理。

P5：

* [ ] 将经过验证的视频模板标准化。
* [ ] 为模板设计版本、参数和依赖声明。

#### 暂不实施

* [ ] 不立即建设完整视频剪辑器。
* [ ] 不自行重写成熟的视频渲染引擎。
* [ ] 不在 P1 阶段开发视频模板市场。

#### 验收标准

* [ ] 可以定义一个可参数化的视频模板。
* [ ] 可以明确渲染输入、任务状态和输出产物。
* [ ] 渲染产物可以进入统一素材体系。
* [ ] 视频模板的依赖和许可证已经核查。

| --- | --- | --- | --- |
| erxes | **AGPLv3**（`ee/` 下 `-ee` 插件为 Enterprise Edition，另附「不得作为 SaaS 与 erxes Inc. 竞争」的限制） | 仓库根 `LICENSE.md` 原文 | **参考重写（第 3 类）**：强 copyleft + 网络条款，不得复制实现代码 |

> **不得**把上表当作「许可证已通过」：除上表各行外，其余来源的核查状态仍为**未核查**（见 §二 各节的勾选框），且已核实的各项也只覆盖仓库自身代码，不覆盖其依赖与素材。

建议将每项候选能力归入以下类别之一：

1. **直接集成**：许可证、技术和维护成本均可接受。
2. **独立调用**：保留项目边界，通过进程、API 或工具接口调用。
3. **参考重写**：借鉴架构或交互，不复制实现代码。
4. **暂不采用**：价值不明确、成本过高或不符合当前阶段。

不得仅凭 README 宣称某项能力“开源”，就认定整个产品、所有依赖、模型和素材都允许自由商业使用。
